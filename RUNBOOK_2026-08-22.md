# RUNBOOK — 2026-08-22 audit: apply, re-run, redeploy

**Purpose.** Fourteen defects were found and fixed across two audit passes
(Part E items 26–41 of `ENGINEERING_CHANGELOG.md`). Every fix currently exists
only as a patch script. **Nothing has been applied to `janus-alpha`, the WFO
re-run has not been done, and the paper state has not been reset.** This is the
order to do those in, why each step is in that position, and what each step
should and should not produce.

**Read this first.** Two of these steps are cheap and reversible (1, 2). One is
expensive and you may decide not to do it at all depending on what step 1 says
(step 4). One is irreversible in the sense that it discards a live record
(step 6, the paper reset — it archives rather than deletes, but the curve
discontinuity is permanent). The order matters in three specific places, all
flagged inline as **ORDER MATTERS**.

**Where.** Steps 1 and 4 want the 15-year `NSE_EQ_Master_Raw.parquet` and are
best run in Colab (see step 0). Steps 2, 3, 5, 6, 7 are local — Windows `cmd`
in the `janus-alpha` checkout is fine, and none of them need the parquet.

## Step 0 — decide where the compute happens (5 minutes)

**Do:** keep using Colab for anything that touches the V9 parquet. Run the
patch scripts and the test suite locally.

**Why.** You asked whether local `cmd` + Python + Claude Code beats Colab for
backtesting. For this work: **no, and it is not close.** The re-run in step 4 is
~28,000 simulations over a 15-year panel. That is bounded by CPU and RAM, not by
tooling ergonomics, and Colab already has the parquet staged and a working
environment. Moving it locally buys you a nicer editor for the part of the job
that is not the bottleneck, and costs you a day of environment setup —
`pyarrow` alone, plus matching pandas/numpy versions to what produced the
existing results.

Where local *does* win is steps 2, 3, 5 and 7: applying patches, running the
test suite, and reading diffs. Those are file-editing tasks with fast feedback
loops, they need no parquet, and the 14 test scripts are pure
pandas/numpy — they run anywhere. So: **local for the code, Colab for the
panel.** That split needs no new setup, because it is what you already have.

**Not expected:** any need to install `pyarrow`, `scipy`, or `gspread` locally.
Nothing in steps 2, 3, 5, 6, 7 imports them. If a step asks for one, something
has gone wrong — stop rather than installing.

## Step 1 — measure the bias before paying for the re-run (Colab, ~2 min + ~15 min)

```python
!python measure_lookahead_bias.py --data NSE_EQ_Master_Raw.parquet \
        --engine wfo_engine_updated.py            # Stage 1 + 1b, ~2 min
!python measure_lookahead_bias.py --data NSE_EQ_Master_Raw.parquet \
        --engine wfo_engine_updated.py --stage2   # adds 2 full sims, ~15 min
```

**Why this comes first.** Step 4 costs ~28,000 simulations. This costs minutes
and tells you the *size* of what you are about to re-measure. Run it on the
**unpatched** tree — it lags the inputs itself, in memory, and compares against
the contaminated path. That is the whole point: it needs both behaviours
available, so patching first destroys the comparison.

**Expect to see:** three verdict blocks. Stage 1 reports how far the Sniper's
entry price, stop distance and position size move once inputs are lagged
(item 26). Stage 1b reports how often the *macro gates* change tier once lagged
(item 32), in units of capacity — slot count and capital share — plus a signed
spread with a Welch's `t`. Stage 2 reports a CAGR and MaxDD for both paths.

**Expect the verdict to be one of three words** and to be trusted only in this
sense: `flattering` (the contamination helped the backtest), `penalising` (it
hurt), or `INDISTINGUISHABLE FROM NOISE` when `|t| < 2`. If you get the noise
verdict for item 32, that is a real result — it means the macro lag is a
correctness fix with little numerical consequence, and the re-run's delta will
be almost entirely item 26.

**Do NOT expect the synthetic-fixture numbers to reappear.** For the record, on
the synthetic panel Stage 1b gave 899 comparable dates, tier changes on 187
(20.8%), spread +0.030% at `t = +0.57` → noise, and Stage 2 gave CAGR
+14.34% → +12.39%. **Those numbers demonstrate that the measurement works.
They are not a preview.** The fixture's breadth is near-random
(autocorrelation 0.891, far below the real panel's persistence), it contains
zero VIX-spike days, and it is 100% BULL — so the `BEAR` allocation branch and
the entire `VIX_Spike` kill-switch are untested by it. Quoting −1.95pp as an
expectation would be inventing a result.

**Also do not read a small change in mean slots as a small bias.** Lagging
shifts capacity *in time*; it does not add or remove capacity on average. The
effect lives in the correlation between when capacity arrives and when returns
arrive. On the fixture the means moved 4.464 → 4.458 while the underlying
tier changed on a fifth of all days.

**Decision point.** If Stage 1 shows a material change and Stage 2 shows a
CAGR drop of more than about a point, proceed to step 4 — you need honest
numbers. If both come back inside the noise floor, the fixes are still correct
and still go in (steps 2–3), but the re-run becomes a lower priority than
getting clean live data, which is where your stated priority already points.

## Step 2 — branch, then apply every fix (local, 10 minutes)

**ORDER MATTERS — branch first.** `apply_fixes.py` has **no `--out` flag**; it
edits in place. `apply_fixes_v2.py` has `--out`, but `apply_fixes.py` does not,
so there is no "preview both" mode. Branch, or you have no clean way back.

```cmd
cd path\to\janus-alpha
git checkout -b audit-fixes-2026-08-22
git status                                    :: expect: clean tree

python apply_fixes.py --fix1 --fix3 --fix5
python apply_fixes_v2.py --macro-lag --idle-yield --run-guard --sheets --live-params
```

**Why one batch and not one fix at a time.** An earlier draft of this advice
said to apply item 26 alone and re-run first. **That advice was wrong and is
superseded.** Item 32 is a *second* look-ahead in the same execution path, so
"26 alone" would have produced a re-run that was still contaminated — a number
that looks like a result and is not one. Every fix that changes backtest
behaviour (**26, 32, 28, 36**) goes in together, then you re-run **once**.

**Why these five v2 flags together.** `--macro-lag` also fixes item 35
(`VIX_Spike` hardcoded `False` in live) because both now call one shared
`compute_macro_regime()`. `--live-params` is the one to care about most:
`generate_live_params.py` carried its own drifted copy of the engine and never
received the idle-yield or CAGR-units fixes, so it was selecting live
parameters with a different fitness function than the backtest that validated
the approach. That is a selection defect in the script that writes what live
actually trades.

**Expect:** each flag prints the files it touched and what it wrote. Both
scripts are idempotent — re-running prints `already contains` and changes
nothing. Both use exact-string replacement with assertions, so a partial patch
exits non-zero rather than half-applying.

**Do not expect** `git diff` to be small. It is roughly **900 changed lines
across five files**, much of it comments explaining the timing convention:
`live_pipeline.py` (~524), `coiled_alpha_logic.py` (~262),
`wfo_engine_updated.py` (~55), `generate_live_params.py` (~44) and
`data_prep_updated.py` (~27).

**`data_prep_updated.py` changing is correct** — do not stop when you see it.
`--macro-lag` routes it through the one shared `compute_macro_regime()` in
`coiled_alpha_logic.py` instead of computing `Regime_Label`, `ATR_10`,
`ATR_Baseline_50` and `VIX_Spike` inline. That de-duplication is the point: it
is what makes it structurally impossible for the backtest and the live pipeline
to drift apart again, which is how item 35 (`VIX_Spike` hardcoded `False` in
live) happened in the first place. If a **sixth** file appears in the diff,
that is worth stopping for.

failure — it will print `already contains` and exit 0, which looks like a fix

## Step 4 — the WFO re-run (Colab, hours)

**ORDER MATTERS — after step 2, and only after step 3 is green.** Re-running
against a partially patched tree produces a number that is neither the old
result nor the new one.

```python
!python wfo_engine_updated.py        # or your existing multi-seed driver
!python run_multi_seed.py            # if you want the seed-variance spread again
```

**Why.** The headline **14.17% CAGR / −29.96% MaxDD** was measured under two
look-aheads and a CAGR units bug. It is superseded and **not yet replaced**.
Until this step runs, every Sniper figure in changelog Parts B/C/D and in the
closure summary is an upper bound, not a result.

**Expect the new CAGR to be lower.** Both look-aheads gave the Sniper sleeve
information it could not have had at fill time — better entry prices, better
stops, better-sized positions, and more slots on exactly the days that turned
out well. Removing that removes an advantage.

**Expect the item 28 fix to move candidate *selection*, not just the printed
number.** `calculate_fitness()` annualised with `365.25 / days` against a
trading-day count, inflating CAGR by roughly 365/252 ≈ 1.45×. That pushed
`norm_sortino = min(sortino/3.0, 1.0)` into its cap and flattened the very
differences the fitness function ranks on: at daily vol 0.006, true Sortino
2.854 vs inflated 4.273; at 0.008, 2.134 vs 3.195. The inflated values
saturate, the true ones do not. So **expect different windows to pick different
parameters**, not merely the same parameters with a smaller number attached.

**Expect the idle-yield change to be small and slightly negative.** The old code
divided the annual rate by 365 and accrued it 252 times a year; compounded, a
stated 6%/yr delivered an effective **4.2291%**. The new basis is a true 4.0%/yr
on /252, which compounds to **4.0807%**. So the change is **−0.1484pp of gross
cash yield**. On 600,000 of cash that is 95.2381/day now versus 98.6301/day
before — a difference of 3.3920/day. Small, and in the honest direction.

**Treat −0.15pp as an upper bound on the CAGR effect, not the expected value.**
Yield accrues only on *uninvested* sleeve cash, so the full −0.1484pp would land
only if capital sat 100% in cash for the whole period. With the sleeves partly
invested the realised drag is smaller — how much smaller depends on the average
cash fraction, which the re-run reports and I have not measured. Items 29 and 36
are a correctness fix; do not treat this figure as a forecast.

**Do NOT expect to hit the original ~20% CAGR / 15–20% DD targets.** The
pre-audit numbers already missed them (14.17% / −29.96%) and the corrected
numbers will be lower still. If a re-run comes back at or above 20% CAGR,
treat that as a bug in the re-run, not a result — check first that the patches
are actually present in the tree the run used.

**Do not chase the target from here.** Your own stated priority is to get to
live infrastructure and learn from real data rather than more historical
curve-fitting, and that is the right call: the gap between 14% and 20% is not
going to be closed by re-tuning the thing that just turned out to be measuring
itself wrong.

## Step 6 — reset the paper state (local, 2 minutes)

**ORDER MATTERS — this is step 6, not step 1.** Resetting before the fixed
code is deployed would just start accumulating a second contaminated segment.

```cmd
python reset_paper_state.py --dry-run     :: read this output before proceeding
python reset_paper_state.py
```

**Why (your decision, "Reset and restart clean").** The existing state cannot
be compared with anything produced after these fixes. The 3 Sniper positions
opened 2026-08-17 were entered at `OPEN(t)` on signals computed from
`CLOSE(t)`, with stops and share counts sized from that same unseeable bar — so
entry price, stop distance *and* position size are all contaminated, and the
open P&L is not a number that means anything. Fills were also recorded under
the old exits-before-rebalance ordering, and nothing prevented re-processing a
bhavcopy.

**Why not "repair" it.** Re-pricing entries at `OPEN(t+1)` would be inventing
history: different entries consume different cash and therefore permit a
different set of *later* entries. There is no local fix to a path-dependent
simulation.

**Expect:** the contaminated state archived verbatim to
`state/archive/paper_portfolio_state.<stamp>.contaminated.json`, an
`archive/README.md` explaining the discontinuity, and a clean state with both
sleeves at 300,000 fully in cash, nothing open, and `last_run_date` set to
`''`. The script derives the required state keys by *reading*
`live_pipeline.py` rather than hardcoding them, and refuses to write if the
pipeline reads a key it does not write.

**Expect it to report `DUPLICATE dates` if item 33 actually bit.** That line
means the duplicate-session bug occurred in practice and not merely in
principle. Worth noting before the evidence is archived.

**Expect the first run after this to credit exactly one session of idle yield
and to NOT be blocked by the duplicate-run guard.** `last_run_date = ''` is
deliberate; both consumers document that case. **Do not seed a date** to make
it look tidier — that either suppresses the first run or invents a yield
catch-up window.

**ORDER MATTERS — `--run-guard` must be deployed before `--idle-yield` is
live.** Both land together in step 2, so this is only a hazard if you
cherry-pick: yield accrual without the duplicate guard means a re-processed
session double-accrues.
